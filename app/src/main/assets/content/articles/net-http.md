# HTTP и REST

Вопросы из этого раздела закрывают базу веб-протокола: методы, идемпотентность, статус-коды, заголовки и REST-контракт.

### Методы и идемпотентность

- `GET` — читает, `POST` — создаёт, `PUT` — заменяет целиком, `PATCH` — обновляет частично, `DELETE` — удаляет
- Идемпотентность: повтор `GET/PUT/DELETE` не меняет результат; повтор `POST` — создаёт дубль. Отсюда правило ретраев: безопасно повторять только идемпотентные методы (для `POST` — idempotency key)
- Ловушка: «401 vs 403» — первый про отсутствие аутентификации, второй про отсутствие прав **после** аутентификации

### Статусы, которые реально обрабатываются в коде

- `200/201/204` — успех (тело/создание/без тела)
- `400` — ошибка клиента, ретрай бесполезен
- `401` → refresh token flow
- `429` — rate limit, ретрай с бэкоффом по `Retry-After`
- `5xx` — вина сервера, ретрай допустим

### Заголовки

- `Content-Type` — формат тела (`application/json`, `multipart/form-data`)
- `Authorization` — токен (`Bearer ...`)
- `Accept`, кэш-заголовки (`Cache-Control`, `ETag`) — реже, но спрашивают

### REST-практики

- Stateless: каждый запрос самодостаточен (токен и контекст в самом запросе), сервер не держит сессию в памяти
- Ресурсы — существительные во множественном числе: `/users/{id}/orders`
- JSON: camelCase-поля, DTO-слой, а не маппинг ответа сервера напрямую в домен

### Питфоллы и собеседование
- Часто спрашивают: «какой метод идемпотентен», «чем 401 отличается от 403», что вернёт сервер на создание ресурса
- Отвечайте через следствия: идемпотентность → политика ретраев; 401 → auth-флоу; 429/5xx → экспоненциальный бэкофф
- Если спросят «а что такое REST по-настоящему» — опирайтесь на HTTP-семантику и stateless, а не на «REST это JSON»

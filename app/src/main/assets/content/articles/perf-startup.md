# Cold start и оптимизация

Закрывает вопросы prs_001–prs_006: типы старта, инициализация SDK, App Startup, план оптимизации.

### Типы старта
- **Cold**: процесса не было → fork (Zygote) → классы/JIT → `Application.onCreate` → `Activity.onCreate` → первый кадр (**TTID**), затем полноценный контент (**TTFD**).
- **Warm**: процесс жив, Activity пересоздаётся (например, её выгрузила система) — дешевле холодного, но дороже hot.
- **Hot**: всё в памяти, окно просто переднего плана — почти нулевая работа.

### Что делает старт долгим
- Тяжёлая инициализация SDK (аналитика, pull-конфиг) в `Application.onCreate`; главное запрещённое: **синхронная сеть до первого кадра** — сотни мс и ANR при плохой сети.
- Content provider'ы библиотек тоже добавляют время — держать список под контролем (AGP/Perfetto — трек App Startup).
- Первый экран без данных → спиннер вместо мгновенной отдачи из Room/кэша.

### App Startup и отложенная инициализация
- `androidx.startup`: `InitializationProvider` (content provider) читает манифестные метаданные и запускает `Initializer`-компоненты до `Application.onCreate`; порядок задаётся через `dependencies()`.
- Чужой автозагрузчик отключается тегом `tools:node="remove"` и инициализируется вручную (`AppInitializer.initializeComponent`) или лениво «при первом использовании».
- Crash reporting допустим рано — он нужен раньше первого падения. Остальное — по потребности.

### Питфоллы и собеседование
- Порядок ответа: замер (Macrobenchmark TTID/TTFD, Vitals) → CPU-трейс → разрезать `Application.onCreate` → lazy → Baseline/Startup Profile → R8 в release.
- Baseline Profile (AOT критических путей) даёт в среднем +20–30% к старту; в связке — `androidx.benchmark.macro` при генерации.
- Спрашивают «сколько стоит холодный старт вашего приложения» — знайте реальные числа и методику замера, а не абстрактную норму.
- Splash Screen API: системный сплэш вместо самодельной Activity — не «оптимизация», а отсутствие лишних кадров в стартовом пути.

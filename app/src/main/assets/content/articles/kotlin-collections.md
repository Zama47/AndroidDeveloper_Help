# Коллекции и ленивость

Эта статья закрывает вопросы ktc_001–ktc_006: read-only vs mutable коллекции, map/filter/reduce/fold, Sequence и сложность операций.

### Read-only ≠ неизменяемое
- `listOf()` возвращает read-only `List` — у него нет `add/remove`, ошибка компиляции, а не рантайма
- Не путать: `val list = mutableListOf(1)` — read-only ссылка на mutable-объект; мутировать можно, если до объекта добрались
- `Collections.unmodifiableList` из Java бросает `UnsupportedOperationException` — в Kotlin этот путь не нужен: отдельные интерфейсы решают на этапе типов

### map / filter / reduce / fold
- `map`, `filter` возвращают новую коллекцию; исходная не меняется
- `reduce { acc, item -> ... }` стартует с первого элемента и падает на пустой коллекции; `fold(initial)` — с заданного аккумулятора, может менять тип результата и справляется с пустым входом
- `groupBy { }` → `Map<K, List<T>>`, `associateBy/associateWith` → `Map<K, T>` ; `distinct()` держит `HashSet` внутри, `contains` aproximadamente O(1)

### Sequence — ленивость
- Промежуточные операторы (`map`, `filter`) последовательности ничего не вычисляют — ждут терминального (`toList`, `first`, `take`, `sum`)
- `.asSequence()` и обратно `.toList()`; элементы текут по всей цепочке по одному — важен порядок операторов: сузить (filter) до тяжёлого (map) дешевле
- Терминальный `first { }`/`take(n)` обрывает обход: хвост даже не трогается
- Ловушка: на маленьких данных sequence может быть медленнее жадной обработки из-за накладных расходов итераторов — ленивость нужна для большого объёма или раннего выхода

### Питфоллы и собеседование
- Классический вопрос: «в чём разница fold и reduce» и «сколько раз сработает map в цепочке с first» — считайте элементы вслух
- Ловушка: цепочка над List строит промежуточные коллекции на каждый оператор — на больших данных это лишние аллокации; asSequence решает
- Уметь на пальцах: Set для уникальности с O(1) contains, Map для «много к одному», read-only по умолчанию в публичных API

# Мокирование

Здесь закрываются вопросы `tsm_*`: иерархия тестовых двойников, MockK (`coEvery`, `spyk`, `relaxed`), что мокать не стоит.

### Тестовые двойники: кто есть кто
- **Dummy** — просто передаётся, никогда не вызывается.
- **Stub** — возвращает заготовленные ответы без логики.
- **Fake** — упрощённая рабочая реализация (in-memory лёгкая БД, FakeRepository).
- **Spy** — реальный объект + учёт вызовов (MockK `spyk`).
- **Mock** — объект с записанными ожиданиями взаимодействий (`verify`).
- Ключевая путаница: fake vs mock — fake проверяется через состояние, mock — через верификацию вызовов.

### MockK — ключевые API
- `mockk<Repo>()` — полный мок; `relaxed = true` — все методы возвращают дефолты (0/пустые коллекции/вложенные моки) без настройки.
- Suspend: `coEvery { repo.fetch() } returns list`, `coVerify { repo.fetch() }`, `coAnswers` для сложных ответов.
- Исключение: `coEvery { repo.fetch() } throws IOException()` — типичный приём для сетевого кейса.
- `spyk(realObject)` — часть методов заглушить, остальная реализация живёт по-настоящему.
- Осторожно: с relaxed-моком неожиданные вызовы тихо вернут пустоту, а не упадут — в серьёзных тестах используйте verify, чтобы удостовериться в вызовах.

### Что не мокать
- value-объекты, DTO, enum'ы — дешевле и надёжнее создать реальный экземпляр: equals/hashCode у моков реализуются библиотекой, сравнения в assertions ведут себя странно.
- Практическое правило: границы I/O (сеть, БД, clock, analytics) — мокаем; алгоритмы и данные — реальные объекты.
- Избыточный мок: «прокэшировать» каждый метод Repository — тест повторяет внутренности класса и краснеет при любом рефакторе.
- Фикстуры: однотипные — через @Before/helper; мини-фабрика `testQuestion(id = ...)` короткая и гибкая; анонимные копии DTO в каждом тесте — невозможно поддерживать.

### Питфоллы и собеседование
- Спрашивают: различия fake/mock/stub/spy, что значит verify, что не мокать, как мокать suspend-функции.
- Смотрите шире: `verifySequence`, `slot<T>()` (захват аргументов), `clearAllMocks`, интеграция с JUnit 5 через `MockKExtension`.
- Ловушка: ответить «fake — это и есть stub» — на middle-уровне различие должны уметь объяснить: state-based тест → fake, interaction-based → mock.

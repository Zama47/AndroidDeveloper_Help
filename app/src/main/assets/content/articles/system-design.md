# System Design для Android-разработчика

## Рамка ответа на собеседовании

1. **Уточнить требования** — функциональные (что строим) и non-functional (DAU, latency, офлайн, шифрование, платформы).
2. **Оценки (back-of-envelope)** — порядки величин для выбора инфраструктуры.
3. **High-level design** — клиент, API-слой, сервисы, БД, кэши, очереди.
4. **Deep dive** — 2–3 узких места с trade-offs (фид, доставка, синхронизация).
5. **Эволюция** — как меняем схему при росте ×100.

## Оценки

| Вопрос | Формула |
|--------|---------|
| QPS | DAU × запросов/день ÷ 86400; × пик 2–5× |
| Bandwidth | QPS × размер ответа |
| Хранилище | сообщений/день × размер × дни |
| Формулы памяти кэша | hot set × размер записи × overhead |

Пример: 10M DAU, 50 req/день ≈ 5.8K QPS средн., 15–30K в пике. Порядки определяют: один Postgres или шарды, CDN, очереди.

## Ключевые концепции

### CAP и консистентность
При partition выбираете **CP** (банки, etcd — отказ вместо рассинхрона) или **AP** (DNS, лента — устаревшее чтение лучше отказа). **Linearizability** — самая строгая модель (дорого); **eventual** — реплики догоняют.

### Шардирование и репликация
- **Реплика** — полная копия: доступность и read scaling.
- **Шард** — часть данных: write scaling; распределение ключей — **consistent hashing** (миграция ~1/N ключей).
- Репликационный лаг: read-your-writes через привязку к мастеру.

### Кэширование
**Cache-aside** (промах → читаем БД в кэш), **write-through**, **write-behind**. Ловушки: invalidation, протухание, «навсегда устаревший» объект. Кэшируем измеренные горячие места, с TTL.

### Очереди
Kafka/PubSub — асинхронизация, буст пиковой нагрузки, fan-out, retry, слабая связанность. События идут с **idempotency key**.

### Идемпотентность
Сеть рвётся — ретраи обязательны. Мутации клиента: UUID мутации, сервер дедуплицирует и отдаёт успех повторно.

### Saga вместо 2PC
2PC блокирует участники при падении координатора. Saga — локальные шаги + **компенсации** (откат бизнеса, не SQL). Оркестрация или хореография.

## Мобильный паттерн: offline-first

1. **Room — источник истины** для UI (мгновенный отклик, оффлайн).
2. Мутации → **outbox** с client_mutation_id + timestamp.
3. **WorkManager** шлёт батчи с backoff + jitter при сети.
4. Pull `/sync?since=last_seq` — серверная лента применяется поверх (монотонный max прогресса).
5. UI индикатор синхронизации; конфликты — явная политика.

## Доставка и real-time

- Активный экран — **WebSocket**/long polling.
- Фон — **FCM**: notification-канал (системный трей) vs data-канал (тихая синхронизация через onMessageReceived + WorkManager).
- Синхронизация по **sequence**, не по времени.

## Фид (ленты)

- **Fan-out on write** (материализуем у подписчиков) — быстрое чтение.
- **Fan-out on read** (собираем при чтении) — для celebrity-аккаунтов.
- Гибрид + cursor-based пагинация (по id, не offset).

## API

- **Gateway**: auth, rate limit (token bucket в Redis), versioning, BFF-агрегация.
- Токены: **access (короткий) + refresh с ротацией**; pinning — осторожно, с планом ротации пинов.
- Rate limit: 429 + Retry-After; на клиенте — свой троттлинг.

## Файлы и медиа

Клиент → **presigned URL** → прямой PUT в объектное хранилище (S3) → событие в очередь → обработка (миниатюры, транскод) → **CDN** на чтении. multipart/resumable для больших файлов.

## Наблюдаемость

Три столпа: **метрики** (RED/USE), **структурированные логи** с trace id, **трейсы**. Мобильная часть: Crashlytics, ANR, network-трейсы. SLI/SLO и алерты по burn rate.

## Multi-tenancy

Row-level (tenant_id, обязателен в каждом запросе) / schema-per-tenant / database-per-tenant. Утечка через забытый WHERE — худший класс багов.

## Что оценивает интервьюер

- Явные **trade-offs** (availability vs consistency, latency vs стоимость).
- Способность к **углублению** после high-level.
- Знание **mobile-реалий**: оффлайн, батарея, FCM-доставка, memory pressure.
- Скромность: «я не знаю Kafka в деталях, но вот как я подошёл бы…».

## Чек-лист для квиз-приложения (наш проект)

1. Контент — статические JSON на клиентах (zero backend для MVP).
2. Прогресс — Room + outbox + WorkManager (см. «Офлайн-синхронизацию»).
3. Рост — свой API + Postgres (user, progress, decks), кэш Redis для leaderboard.
4. Push — тихие data-пуша для «нового набора карточек».
5. Безопасность — access/refresh, серверная валидация, идемпотентность мутаций прогресса.

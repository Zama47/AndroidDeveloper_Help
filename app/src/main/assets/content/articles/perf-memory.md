# Память и утечки

Закрывает вопросы prm_001–prm_006: утечки через Context/static, LeakCanary, bitmap, GC.

### Как утечёт Activity
- Долгоживущий объект (singleton, `object`, `companion`) не должен держать `Activity`, `Fragment`, `View` — они сильнее своего жизненного цикла. Безопасен `Application context`.
- Ловушка: `listener`'ы, `BroadcastReceiver`, подписки Event/LaunchedEffect-объекты, незакрытые `Handler`-runnable из-за не-статических inner-классов — всё это удерживает внешний экран.
- Job корутины/таймеры, не отменённые в `onDestroy`, — тоже удержание экрана.

### LeakCanary
- В debug-сборке автоматически следит за Activity/Fragment/ViewModel/View через weak references: GC не очистил → heap dump → анализ (Shark) → трейс до GC root.
- Умеет дедуплицировать одинаковые утечки и показывать retaining-объекты в приложении. В release не добавлять.
- Heap dump в Android Studio Profiler: смотреть Retained Size и dominators — кто реально держит память, а не просто большой.

### Bitmmap и GC
- Память битмапа = width × height × bytes/пиксель: ARGB_8888 — 4 байта (1080×1920 ≈ 8.3 МБ), RGB_565 — 2 байта без альфы; HARDWARE — память на GPU.
- Дисковый размер (JPEG-файл) ≠ памяти. Грузить с downsample (`inSampleSize`) под размер View, `LruCache` с лимитом (~1/8 heap).
- GC автоматически освобождает недостижимые объекты: `System.gc()` «лечит» только подсказками — если OOM, объект кого-то удерживал.

### Питфоллы и собеседование
- Типовой вопрос: «какие утечки вы находили?» — назовите 2–3 реальные истории с инструментами (LeakCanary + трейс до корня).
- Не путать leak и просто «много памяти»: рост heap может быть жизненным циклом кэша, а не утечкой. Диагноз — по тренду повторов (LeakCanary группирует одинаковые трейсы).
- onTrimMemory — контракт с системой: срезать кэши/пулы, когда системе больно по памяти.
- Питфолл: держать Bitmap в статике и «recycle» при повороте — двойная ошибка; правильный путь — LruCache под лимитом, а не статика.

# Flow: холодные и горячие

Эта статья закрывает вопросы crf_001–crf_006: cold flow, операторы, StateFlow vs SharedFlow, collect, catch/retry.

### Холодный flow
- `flow { emit(...) }` — функция построения: код выполняется заново на каждую подписку; до первого `collect` ничего не работает
- Следствие: два подписчика на networkFlow = два сетевых запроса; если нужен один источник на многих — `stateIn`/`shareIn`

### StateFlow vs SharedFlow (оба горячие)
- `StateFlow` — «последнее состояние»: обязательно начальное value, склеивает (conflate) и дропает дубликаты; почти эквивалент mutable-поля, о котором можно узнавать
- `SharedFlow` — шина событий: без начального значения, `replay`/`buffer`/`extraBufferCapacity`, отдаёт каждый эмит; для подписчиков, которые «пришли после» события, без replay — потеря
- Превращение сырого потока в состояние: `flow.stateIn(scope, SharingStarted.WhileSubscribed(5000), initial)` — держит upstream при переходах конфигурации

### Операторы
- `catch { }` — перехват исключений вверх по потоку (upstream), исключение в collect-блоке не перехватит; `try/catch` вокруг collect ловит всё
- `retry { }` пересобирает upstream после ошибки; `retryWhen { cause, attempt -> }` — с экспоненциальной паузой
- `distinctUntilChanged` подавляет дубликаты подряд; `conflate`/`buffer` — для мягкости, если коллектор не успевает (конфлюация пропускает промежуточные значения)

### Практика в UI
- Состояние: `StateFlow` + `collectAsStateWithLifecycle` / `repeatOnLifecycle`; события: `SharedFlow(replay = 0)` или `Channel` + `receiveAsFlow`
- Ловушка: one-shot события в StateFlow повторяются при каждом повторном касании (повторная подписка — возврат экрана)

### Питфоллы и собеседование
- Топ: «что будет у двух подписчиков на flow», «чем StateFlow отличается от SharedFlow», «что перехватывает catch»
- Ловушка: `catch { }` в конце цепочки не поймает ошибки встроенных выше операторов, если стоит ниже них; помните направление потока
- Уметь обосновать: событие ≠ состояние — для навигации и snackbare отдельный канал

# Clean Architecture

Слои, границы зависимостей и когда это оверкилл.

### Слои
- **Presentation** — ViewModel + UI, знает только про домен.
- **Domain** — use cases и модели бизнес-логики, не зависит ни от чего (чистый Kotlin-модуль).
- **Data** — реализации репозиториев: Room, Retrofit, DataStore; маппинг DTO → domain-модели.

### Правила зависимостей
- Зависимости направлены **внутрь**: presentation → domain ← data. Domain ничего не знает о фреймворке.
- Repository — интерфейс в domain, реализация в data: UI не знает, откуда данные (сеть, БД, кэш).
- Use case — одна бизнес-операция; если это просто `repo.getX()` без логики, многие команды пропускают слой.

### Питфоллы и собеседование
- «Зачем маппинг DTO→domain?» — чтобы сетевые модели не протекали в UI и не ломали экран при смене API.
- Оверкилл: для крошечного приложения 3 слоя + use cases на каждый чих — избыточно; признай это на собеседовании, это плюс.
- Однонаправленный поток данных (UDF): события вверх, состояние вниз — и в MVVM, и в MVI это общая идея.

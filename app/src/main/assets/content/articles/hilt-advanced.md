# Qualifiers и DI в тестах

Здесь закрываются вопросы `hla_*`: `@Qualifier`, `@Binds` vs `@Provides`, подмена зависимостей при тестировании с Hilt.

### @Binds vs @Provides
- `@Binds` — abstract-метод без тела, связывает интерфейс/базу с имплементацией: минимальный код, работает только в abstract-модуле.
- `@Provides` — функция, где объект собирается вручную (билдеры, сторонние SDK); модуль может быть `object`.
- Канон выбора: есть свой класс с @Inject-конструктором → связка через @Binds (или вообще без модуля); есть чужой класс со сложным созданием → @Provides.

### @Qualifier и @Named
- Две привязки одного типа без квалификатора = duplicate bindings, ошибка компиляции.
- Варианты: свои аннотации `@Retention(BINARY) @Qualifier annotation class DebugApi` или встроенный `@Named("debug")`.
- Квалификатор ставится и на биндинг (`@DebugApi @Provides fun api(...)`), и на точку инъекции (`@DebugApi private val api: Api`).
- Ловушка: рассчитывать на имя параметра — оно роли не играет; тип + квалификатор = ключ привязки.

### Подмена зависимостей в тестах
- Схема: `hilt-android-testing` + `HiltTestApplication` + тест-класс:
  - `@HiltAndroidTest` — активация контейнера в тесте;
  - `HiltAndroidRule` — первым правилом (order = 0), вызывает `inject()` в `setUp`;
  - `@UninstallModules(ProdModule::class)` — удаляет привязки production-модуля;
  - тестовый модуль с `@TestInstallIn` или поля `@BindValue`.
- `@BindValue` — значение поля становится привязкой на время теста (свежий instance на каждый тест); коллекции — `@BindValueIntoSet/Map`.

### Питфоллы и собеседование
- Спрашивают: @Binds vs @Provides (и когда какая), зачем нужен квалификатор, как подменить зависимость в UI-тесте с Hilt.
- Смотрите шире: `@TestInstallIn` (глобальный для всех тестов), мульти-биндинги (`@IntoSet`, `@IntoMap`), `EntryPointAccessors` для тестовых утилит.
- Опытный ответ: тест подменяется не мок-библиотекой «поверх», а на уровне контейнера — в тесте собирается свой маленький DI, и fake — это тестовая привязка, а не магия.
- Ловушка: забыть @UninstallModules при добавлении @BindValue того же типа — получите duplicate binding при компиляции тестов.

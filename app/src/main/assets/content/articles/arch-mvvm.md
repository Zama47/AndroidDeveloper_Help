# MVVM и ViewModel

Базовый архитектурный паттерн Android: кто владеет состоянием экрана.

### Зачем ViewModel
- Переживает поворот экрана и изменения конфигурации — UI-состояние не теряется.
- Держит ссылки только на данные и логику, никогда на View/Context (утечка).
- Закрывает границу между UI и слоем данных: экран общается только со своим ViewModel.

### LiveData vs StateFlow
- `StateFlow` — современный выбор: холодная логика + `stateIn(scope, SharingStarted.WhileSubscribed(5000), initial)`.
- `WhileSubscribed(5000)` останавливает上游-поток, когда UI ушёл в фон и не вернулся за 5 секунд — экономия ресурсов.
- События (показать снекбар, навигация) — не состояние: каналы/одноразовые флаги, иначе события «переигрываются» после поворота.

### Питфоллы и собеседование
- ViewModel ≠ замена `onSaveInstanceState`: process death ViewModel не переживает — для этого `SavedStateHandle`.
- Не прокидывай ViewModel в дочерние экраны чужого флоу — это связывает экраны намертво.
- Вопрос-ловушка: «два экрана делят один ViewModel» — только в рамках одного navigation back stack entry (scoped по навигации).
